基準開発版には区間削除・Undo/Redo・計画履歴・空計画整理の変更を含むが、GUI受入は未完了。CI結果は対象HEADごとに確認し、GUIの見た目・入力感・保存実操作の合格を代替しない。本候補には平行敷設と交差ホームの駅グループ/共有名称/情報表示を統合済みだが、ネイティブGUIは未確認。駅グループは物理ホームIDと経路参照を保持し、撤去は個別ホーム単位。
現在の制約は [建設操作](track-construction-interaction.md)、[系統](operating-services.md)、[保存](storage.md)を参照。

## 2. 直近の順序（作業案、日程・機能追加の確約ではない）

1. **建設・保存の実機受入**: 直線/円弧、両端延伸、既存/計画駅、複数経路・個別着工、手動/自動保存、再読込。既存セーブとは別のテストワールドで実施し、旧版へ戻す場合は旧セーブのコピーを用いる。
2. **0.1の編集経路を閉じる**: 新方式RoutePath/ServicePathの既存編集・部分区間選択の設計。停車出現参照、系統利用中の設備、出典保護、候補全体の原子的適用を先に決める。旧Track編集を実装し直さない。
3. **運行の最小縦切り**: 共通時計・簡易ダイヤ・車両性能・駅間走行をRust共通処理に置く。短駅間の最高速度未到達を試験し、その運転時分を旅客側も使う。
4. **固定小地域ODから流動へ**: [需要・流動計画](demand-flow-plan.md)の段階A/B。外部データ未取得でも合成fixtureで保存則・経路配分・性能を検証する。
5. **目的/時間帯・運賃/収支・規模拡大**: 同計画の段階C/D。人口変動やマルチ通信の本実装を同時に詰め込まない。

分岐は必要な将来機能だが、端部延伸の依頼から自動的に着手しない。専用の設備グラフ・進路競合の設計と運行基盤の接続を確認して範囲を決める。

## 4. 実装時の共通完了条件

- 対象・非対象・失敗時の挙動を先に明記し、既存の保存/参照/所有権を保護する。
- 自動試験・静的検査・該当CIと、必要なGUI受入を分けて記録。未実施を成功扱いしない。
- 変更はクラウドで作業し、作業開始時にブランチをリモート作成、区切りごとにcommit/pushして反映確認する。
- mainへのmergeはユーザーが確認した対象・範囲に限る。未統合・他人作業・未保存のブランチを整理名目で消さない。
- 作業完了時に本書の状態と詳細仕様を更新。設計だけなら実装ありへ進めない。
