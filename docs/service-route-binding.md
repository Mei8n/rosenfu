# 路線と系統の明示的関連付け

## 保存上の意味

路線の所属駅、系統の物理経路、系統の停車位置は別の情報として保持する。
関連付けを変更しても、系統の経路・停車設定を自動変更しない。

schema 17 の `service_route_bindings` は系統ごとに次のいずれかを保存する。

- レコードなし: **未確認**。旧データから関連路線を推測しない。
- `binding: {kind: "independent"}`: 利用者が明示的に路線から独立とした系統。
- `binding: {kind: "route", route_id: "…"}`: 利用者が指定した路線との関連。

schema 16 以前の系統は未確認として読み込み、既存のID・経路・停車・駅を変更しない。
新形式で保存したファイルを古い版で読むことはできない。元の旧セーブは上書きせず保護して検証する。

## 操作と整合性

- 路線区間を選んで作る系統は、新旧形式とも選択した路線IDを保存APIへ明示的に渡す。
- 既存系統は、路線または独立を選択して「関連付けを適用」で確定する。
- 未適用の選択は書き込まない。取消では元の関連付けを保持する。
- 路線指定が現在の物理経路と一致しない場合は理由を表示し、候補を残す。
- 変更後の路線でも関連系統の物理経路が成立するか、部分区間・逆方向・区間の順序を検証する。
- 無関係と明示された系統の存在だけを理由に更新を拒否しない。
- 未確認の旧系統がある場合は安全を確認できないため保守的な制限を維持し、明示的な関連付けを促す。
- 路線、系統経路、関連付けの更新はバックエンドでまとめて検証し、失敗時は全体を変更しない。

## 実装・検証の境界

UI は `set_service_route_binding` と、新規/再設定APIの `sourceRouteId` に依存する。
UIだけを旧バックエンドと組み合わせて反映しない。schema移行・包含判定・原子更新はバックエンド側の検証が必要。
複数路線を組み合わせる系統との関連付けは、この単一路線契約では未対応。推測で補完しない。
