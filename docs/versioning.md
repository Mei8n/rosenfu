# バージョン管理

## ゲームの版番号

`MAJOR.MINOR.PATCH`に開発段階を付けます。

| 例 | 用途 |
| --- | --- |
| `0.1.0-alpha.1`、`0.1.0-alpha.2` | 0.1段階の試験配布 |
| `0.5.0-alpha.1` | ベータ前の統合検証 |
| `0.6.0-beta.1`、`0.6.0-beta.2` | ワールド互換を維持する試験配布 |
| `1.0.0-rc.1` | 正式版候補 |
| `1.0.0` | 初回正式版 |
| `1.0.1`、`1.1.0` | 正式版後の修正、機能追加 |

Gitタグは`v0.1.0-alpha.1`のように`v`を付けます。公開済みタグや配布物は差し替えず、修正は新しい版で公開します。
アルファの破壊的変更は許容しますが、その都度明記します。ベータ以降は版番号の大小にかかわらず[ワールド互換方針](world-compatibility.md)を適用します。
メジャー番号を増やすことだけを理由に、ワールド互換を打ち切りません。

## 独立して管理する番号

- **ゲームバージョン**: 利用者が選ぶ配布物の識別。
- **ワールド形式バージョン**: 保存内容の構造を識別する単調増加の整数。移行が必要な変更時に更新。
- **通信プロトコルバージョン**: クライアントとホストの接続可否を判断する番号。初期は一致を必須とする案。

必要に応じて統計・地図などのデータセット版とシミュレーションモデル版も保存します。
ワールド形式が同じでも計算結果が変わる更新はあり得るため、モデル変更をリリースノートに記載します。

## ブランチと公開

既定ブランチ`main`へ、短命な`docs/...`、`feat/...`、`fix/...`ブランチからPRを作成します。
常設のdevelopブランチは初期には設けません。1 PRは1つの目的とし、可能ならもう1人がレビューします。
リリース時は対象コミットの確認後にタグを付け、GitHub Releasesへ変更点、既知の制約、保存互換、復旧方法を記載します。
初期の文書追加だけでゲームのリリースタグを作成しません。

Issueは対象段階、目的、完了条件、依存関係を記載します。ロードマップが範囲、Issueが進捗の管理元です。
期限は作業量が見えてから設定し、将来機能をすべて先にIssue化することは避けます。
