# 描画レイヤーと再計算の境界

## 構成

- `App.tsx`: Worldと編集state、地図操作、スナップ・検証、建設プレビューと操作ガイド。イベントのガードもここで維持する。
- `BuiltTrackLayer.tsx`: 確定済み線路、構造物、線路のヒット領域。World由来の構造物区間分割を`useMemo`で保持する。
- `TrackRenderGeometry.tsx`: 既存の物理線路・分岐描画。`React.memo`を適用する。
- `StationLayer.tsx`: 確定済み駅のホーム・駅名・クリック領域。建設中の駅とのグループ関係も表示に反映する。
- `RouteLayer.tsx`: 路線割当の強調、系統の帯。既存の`routeAppearance`と`serviceRenderChains`の結果を使う。
- `ReferenceGraphLayer.tsx`: 既存のメモ化済み参考線描画をそのまま使う。
- `JunctionPoints.tsx`: 既存の分岐ポイントに`React.memo`を適用する。接続配列はAppで参照を安定させる。
- `SlopeBoundaryMarkers.tsx`: 確定済み線路と建設プレビューの境界計算を別々にメモ化する。

分離したレイヤーはFragmentを返し、SVGにラッパー要素を増やさない。描画順、ヒット領域、イベント透過、CSSクラスは従来のまま。建設プレビューと操作ガイドはSVG内で交互に配置され、イベントも編集stateに依存するため、今回はそれらを包むだけのコンポーネントは追加していない。

## メモ化の条件

`React.memo`は標準の浅い比較を使う。カーソル位置、建設候補線、ホバー情報は確定済みレイヤーのpropsに渡さない。World由来の配列・Mapと、選択・ホバーのコールバックを安定させることで、マウス移動でそれらの描画関数を呼び直さない。

カメラが変われば投影を更新する。確定済み構造物の区間分割はカメラに依存せず再利用する。Worldが置き換われば参照が変わり、構造物・駅・路線を更新する。選択、表示タブ、駅名表示、駅グループ、操作可能状態など表示に関係するpropsの変更でも再描画する。既存のWorld更新はイミュータブルであることが前提となる。

## 検証

`npm test -- src/MapLayersPerformance.test.tsx`で実際のAppを操作する。React.memoの内側の描画関数を計測し、テスト用の追加メモ化で問題を隠さない。

64点の複線線路1本、駅20個のfixtureで、駅配置モードのカーソル移動10回を比較した。変更前（`c92bd41`）のAppを使った一時的な計測テストでは、`displayInfrastructureSections`と`schematicTrackPaths`を各10回呼び出した。変更後は両方0回。確定済み線路・駅・路線・物理線路の描画関数も、同じ10回の移動に対してそれぞれ0回だった。物理線路を使う場合も別途検証している。

回帰テストではさらに、建設候補線と線路ホバーの更新、系統帯が表示されている場合の再利用、カメラ移動後のSVG座標変更、World更新後の駅名と描画更新を確認する。

`npm test -- --maxWorkers=2 --reporter=dot`は176ファイル・1108テスト成功、1ファイル・2テストskip。変更前の通常並列実行で5件の5秒タイムアウトがあったため、全体の検証では並列数を2に制限した。`npm run build`（TypeScript型チェックを含む）と`git diff --check`も成功。ビルドには500 kB超のチャンク警告が残る。

実ブラウザの描画CPU時間・paint時間・FPS・大規模Worldでの所要時間は未測定。テストの`jsdomPointerMs`はReact・イベント・jsdom処理を含む経過時間であり、描画CPU時間や性能向上率を表さない。

## 残る処理

App自体はカーソル更新で再実行される。スナップ探索、建設候補線、検証用リクエスト、編集中・退避中の計画や操作ガイドのSVG生成などは残っている。カメラ移動では各可視レイヤーの投影計算が必要で、World全体が置き換わった場合は変更のない部分も再描画される。大量の線路・駅に対する探索の改善や表示範囲による絞り込みは、実Worldで計測してから判断する。
