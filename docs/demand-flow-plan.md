# 需要・流動の実装計画

更新日: 2026-11-15。**未実装の設計案**。メッシュ主体・遠距離でゾーン要素を取り入れる方向は本人の最新希望。以下の型名・式・区分は実装済み契約ではない。

## 1. 変えない要件

人口/土地用途/目的地から潜在移動需要を作り、鉄道のない地域にも保持する。Work / Errands / Leisure / Attractionsの4分類を基本とし、平日/休日と時間帯・方向を反映する。ゲーム駅は需要へアクセスする設備であり、OSM実在駅の存在・名称・表示ON/OFFを初期需要の発生条件にしない。

人口 → 潜在OD → 鉄道/代替手段と経路への配分 → 実輸送/積み残し → 運賃収入

この各段階を別に保持する。乗換による延べ乗車数とODの人数、未利用と容量不足を混同しない。空港・観光は施設の集客と周辺人口を分け、施設未収録を真の需要ゼロとして扱わない。

## 2. 空間モデル案

- `Mesh` に居住人口、就業/就学・用途・施設、データの出典/時点/推計/欠落を保持する。
- 各メッシュを都市・生活圏などの `Zone` に対応付ける。近距離はメッシュ間、遠距離はゾーン間を主に推計し、発着側メッシュへ人口/目的地属性で配分する。
- 同じ需要をメッシュODとゾーンODへ二重加算しない。目的・距離等による適用範囲と重複除去の規則を決め、ゾーン合計と配分後メッシュ合計の一致を試験する。
- 駅アクセスはゲーム内駅から求める。近くの1駅だけへ必ず割り当てず、徒歩・将来の接続交通と有力候補の保持を検討する。
- 全国の全メッシュ対を常時総当たりしない。疎なOD・候補目的地削減・階層集約を比較する。ただしメッシュ幅、ゾーン境界、距離閾値、候補数は未決で、単純な最寄り固定を確定仕様にしない。

## 3. 手段・経路選択案

アクセス＋待ち＋乗車＋乗換時間、運賃、混雑/満足度を共通の評価尺度へ変換する案を比較する。時間価値・重み・分配関数は未決。時間と満足度に同じ効果を二重計上しない。

車等は初期には集約した代替手段の時間/金銭費用で表し、個別自動車の全走行やバス経営まで前倒ししない。鉄道に必ず乗せず複数経路へ分配する。極端な高運賃・運休・未接続・長距離・フィーダー有無で単調性と納得感を検証する。

[日本向け運賃案](japan-fare-model-notes.md)の同社内通算・路線別率・特急料金等を検討するが、金額/方式は未確定。探索時の見積と課金は同じ規則/版を使い、路線重複で倍率や初乗りを二重適用しない。

既存の建設候補APIは旅客探索器ではない。運行方向・停車・時刻/待ち・運賃・容量を含む旅客用契約を別に設計する。候補打切りを「経路なし」と断定しない。

## 4. 時間・性能・同期案

基礎統計は事前処理してローカルデータパックに収録する案。実装/配布前に利用条件を確認する。ゲーム中はOD×目的×時間帯の集団を扱い、全国の旅客一人ずつを毎フレーム探索しない。

工業地域への朝流入/夕流出、昼の減少、休日観光、空港アクセスと従業者通勤を別fixtureにする。時間帯パターンと経路選択は別更新にし、人口変動はさらに低頻度の地域集約とする。成長率上限・土地容量・便益逓減を検討し、人口固定でも流動再配分する。

路線・ダイヤ・運賃変更時は依存関係から影響を受けるOD/候補経路を再計算する。新線が遠方の経路へ影響するため、単なる近傍地域だけで切らない。依存の無い新しい候補を見落とさない無効化規則と定期的な全体参照比較を用意する。

シングルとホストで同じRustルールを使い、マルチではホストが操作順・計算結果を確定して差分/集計を配信する案。内部通信サーバーの起動自体は必須としない。途中参加/再送でOD・乗車・収入を二重計上しない。モデル版・データ版・乱数seed・計算epochの管理も検討する。

処理を小分けし描画を止めない設計、キャッシュ破棄、全体再計算との差・入力遅延・CPU/RAM・通信量を測定して予算を決める。性能保証や固定更新間隔をまだ宣言しない。

### 7.1 実装単位と順序

1. **0.2・参照エンジン**: 合成人口/目的地と固定ODをRustで保持。潜在需要、鉄道利用、他手段、未達を分離し、全量再計算を正解比較器にする。実データ導入前に欠測とゼロを区別する。
2. **0.2・旅客グラフ**: 既存の物理経路と路線/系統の関連から、方向・停車・乗車・下車・徒歩を構築する。同名/同一駅groupだから物理線路が接続するとは扱わない。別名・未統合駅にも明示的な連絡通路の歩行辺を追加できる契約にする。
3. **0.2・選択と配分**: 複数アクセス駅と有効な系統を比較し、乗車時間、待ち、乗換、運賃を評価。会社を跨ぐ見積と課金を同じ規則版へ揃える。まず小規模で全量探索し、候補打切りを診断できるようにする。
4. **0.3・4分類と日本データ**: 第5節の採用ゲートを通した人口/雇用/通学/施設/広域統計を目的別に導入する。平休日・往復方向・時間帯を分け、集計統計との一致とゲームとしての反応を別評価する。
5. **0.3・容量と経営**: 積み残しによる追加待ちと混雑を反復計算へ反映し、収束しない場合は近似/未収束を表示。勝手な待ち上限で需要消失を隠さない。便益・満足度と一般化時間に同じ不便を二重加算しない。
6. **規模拡大・0.4マルチ**: 疎OD、目的地別集団配分、キャッシュと小分け処理を測定して採用。シングルとホストで同じ計算を使い、モデル版/データ版/seed/epoch/反復番号を結果に付ける。古い結果、再送、途中参加で輸送や収入を二重確定しない。

需要計算は0.1の建設機能へ前倒ししない。ただし物理区間、駅/ホーム、路線、系統、停車点、会社のIDと参照を将来の旅客グラフが利用できるように維持する。

### 7.2 受入fixtureと測定

- 鉄道なし、駅追加のみ、未接続駅、欠測地域、真の人口ゼロを別々に確認する。
- 同じ行先へ行く2系統の増発と、途中で別方向へ分かれる系統の増発を比較し、無効な頻度の合算を防ぐ。
- 普通/急行、部分重複、方向別運行、環状、他社直通、別駅名の徒歩乗換を確認する。
- 高運賃、運休、長い乗換、容量不足時に需要が消失せず、他手段・未達・積み残しへ説明可能に配分されることを確認する。
- ODの人数保存、乗換による延べ乗車の増加、見積/課金一致、同一epochの再実行で二重課金しないことを確認する。
- 新線が遠方ODを変えるfixtureで差分更新と全量再計算を比較する。古い経路依存関係だけを使い、新しい有力経路を見落とさない。
- 駅数、系統数、停車点数、非ゼロOD数、目的数、時間帯数、反復数を入力軸として、CPU時間、ピークRAM、UI遅延、ホスト配信量を測定する。現時点で全国規模性能や許容誤差を保証しない。

### 7.3 未確定値と権利

メッシュ幅、距離帯、アクセス範囲、徒歩速度、時間価値、運賃感度、配分式、時間帯別発生率、容量反復の収束閾値、更新周期、性能予算は未確定。TrainsWorldの定数は実測値でも本人承認値でもなく、そのまま採用しない。

[TrainsWorld NOTICE](https://github.com/circularsquare/trainsworld/blob/main/NOTICE.md)はコードAGPL-3.0とデータの個別条件を案内する。ODbL対象や非商用条件を持つ境界データ等があり、公開リポジトリであることはゲームへの自由な同梱許可ではない。本計画は仕組みの比較であり、コード・パック・素材を複製していない。実装はRosenfuの要件から独立して設計し、日本の各データ配布版の権利を別に確認する。
