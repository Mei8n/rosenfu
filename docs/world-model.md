# ワールド基本モデル（初期実装）

Issue #3 の設計・実装を段階的に進めるための土台です。安定した保存形式ではありません。
実装は `crates/rosenfu-core/src/world.rs` に置き、UI・Tauri・データベースから独立させています。

## 現在の境界

| データ | 責務 |
| --- | --- |
| Player | 操作者の識別。ログイン認証情報は保持しない |
| Company | Player を所有者として参照。プレイヤーとの同一視を避ける |
| Station | 所有会社、名称、WGS84 の緯度・経度 |
| Track | 所有会社と両端の駅。現在は双方向の接続のみ |
| Route | 所有会社、起点、順序付きの線路参照。線路設備を複製しない |
| OperatingService | 路線と独立した運行経路と停車位置。時刻や種別は持たない |

ID は種類ごとの型で区別する非ゼロ整数です。同じ種類の中で一意とし、名称や
配列位置を識別子に使用しません。改名・並べ替えでは ID を変更しません。
採番器はワールドごとの単調増加カウンター `next_id` を保持し、
削除した ID を再利用しない方針です。ネットワーククライアントで採番せず、
現在はコアの追加コマンドが採番します。マルチプレイ導入時も権威側のエンジンで採番します。

## 整合性と編集

`WorldDraft` は編集・デシリアライズ用の候補です。`World::new` または
`World::replace` で検証し、不正な候補を稼働中の `World` に適用できないようにします。
候補の置換に失敗した場合、既存のワールドは変更しません。

検証対象は ID の重複・ゼロ、空白だけの名前、参照先の存在、有限かつ範囲内の座標、
同一駅を両端に持つ線路、空の路線、路線・系統の接続順序、系統の停車位置です。線路はどちら向きにも
辿れます。環状路線や同じ線路の再使用は現段階では禁止しません。

参照中の駅・線路・会社・プレイヤーの単独削除は拒否します。関連する参照の変更や
削除を一つの候補にまとめて検証することで、意図した一括編集を可能にします。
権限チェックは別途必要です。所有会社が異なる設備の参照が整合的であることと、
プレイヤーに編集権限・線路使用権があることは同義ではありません。

## 保存と再生成

合成ワールドの単体テストで、3 駅・2 線路・1 路線を使用しています。
上表のデータと採番状態は保存対象です。空間索引・経路探索グラフ・描画データは
元データから再生成します。現段階ではキャッシュや需要データを追加しません。
Serde による構造の入出力に加え、ファイル保存を独立した storage クレートへ分離します。SQLite とスキーマ移行は未実装です。
読み込み時も必ず検証し、デシリアライズ成功だけで有効なワールドとは見なしません。

## 後続の設計

- 運行系統・列車種別・停車駅・ダイヤは Route/Track に埋め込まず、独立したデータにする。
  複数路線を経由する系統を考慮し、系統の経路表現は簡易ダイヤ導入前に確定する。
- 線形・距離・単複線は Track の設備情報として追加する。現在の端点接続だけで
  運転時間や線路容量を計算しない。
- 日付とシミュレーション時刻はワールド共通の状態として保持する。UI の実時間と分離する。
- 人口・需要・流動・経営は別モジュールに置く。計算上の収支と資金残高を分け、
  将来の非アクティブ時の残高凍結を可能にする。
- 子会社は Company 間の関係として追加し、Player と Company の分離を維持する。
- バスは鉄道の Track に無理に埋め込まず、交通モードを区別する拡張を検討する。
- ベータ移行前に保存スキーマ、移行、バックアップ、互換性テストを整備する。

現実装は小規模な検証用で、参照探索は線形走査です。全国規模のデータ投入前に
索引と編集差分検証を導入します。運行系統は[基本構造](operating-services.md)を追加していますが、運行計算と保存形式はアルファ向け検証段階のため、
この変更だけで Issue #3 を完了扱いにはしません。

## 採番コマンドと外部表現

`add_player`、`add_company`、`add_station`、`add_track`、`add_route`、`add_service` が新規 ID を採番します。
入力エラー時にはデータもカウンターも変更しません。上限到達時はエラーを返し、折り返しません。
`replace` は既存エンティティの編集・削除に限定し、新規 ID の注入やカウンターの変更を拒否します。
削除して保存・再開してもカウンターを保持するため、通常の編集経路で ID を再利用しません。
保存ファイルの手動改変や過去のバックアップへの復元を検出する仕組みではありません。

Rust 内部 ID は `u64`、JSON では ID と `next_id` を十進数文字列で交換します。
JavaScript の安全整数上限を超えても精度を維持し、フロント側では `number` に変換しません。
ゼロ・符号付き・先頭ゼロ・範囲外・JSON 数値は読み込み時に拒否します。
これはまだリリースされていない初期モデルの変更であり、旧数値 ID 形式の移行は提供しません。
