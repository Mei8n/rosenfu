# 運行系統の基本構造

## 現行モデル（schema 18）

設備は Alignment とその端点接続、路線は Route と必須の RoutePath、系統は OperatingService と必須の ServicePath で表す。旧式の駅間 Track、Route.tracks、OperatingService.tracks/stops と旧編集 API は廃止する。旧セーブをこの構造に自動変換しない。[保存仕様](storage.md)を参照。

OperatingService は独立した ID、所有会社、名称、起点駅を持つ。ServicePath は `service_id`、`next_leg_key`、順序付き `legs`、停車参照 `stops` を持つ。各 leg は安定したキーと Alignment または接続 Alignment の区間を参照する。設備は複製しない。

停車参照は駅名や表示順ではなく、始点専用参照または区間キーと駅 ID で識別する。同じ駅の複数回訪問を混同しない。端点は停車固定で、中間駅の追加によって既存停車位置をずらしたり自動停車にしたりしない。路線所属駅と系統停車駅は別の情報。

## 作成と編集

- 単一路線の全区間、部分区間、逆方向を独立した系統として取り込む。対象は Alignment と接続 Alignment。
- 全駅停車または個別指定をユーザーが選び、所属外の駅も含めて確認する。停車図は停車・通過を区別し、同じ経路上の複数系統で異なる停車設定を保持する。
- 保存済み系統名と停車・通過を編集できる。通常の停車編集では系統 ID・経路・leg key を維持する。
- 経路の再設定は別操作。新経路をプレビューして停車方針を選び直す。旧停車設定を自動移植せず、廃止した leg key を再利用しない。
- 未適用編集を別の選択で黙って捨てない。失敗・保存済みデータとの競合時は入力を保持し、ワールドを変更しない。
- 適用とファイル保存は別操作。系統編集のグローバル Undo/Redo、複数路線をまたぐ任意の経由指定は未対応。

## 路線との明示的な関係

`service_route_bindings` は関連路線または独立を明示する。形状や名前から推測しない。未確認が残る場合は理由を示して路線経路編集を保護する。単一路線上の連続した物理部分経路なら逆方向も関連付けられる。複雑な往復・反復や複数路線を横断する関連は未対応。

関連系統が使えなくなる路線変更は原子的に拒否し、既存の系統・停車を自動変更しない。明示的に無関係と判定できる系統だけで他の路線の変更を妨げない。関連と系統経路を同時に変更する操作も一括検証する。

## 参照保護と未実装範囲

使用中の設備・駅を黙って連鎖削除しない。接続区間の撤去は不要な端点リンクのみ解除し、残存設備・駅を維持するが、路線・系統が参照する区間や重なるホームがある区間は拒否する。

列車走行、ダイヤ、車両数、乗客数、収支、乗換効果はこのモデルの完成をもって実装済みにはならない。未計算値を架空の数値で埋めない。ネイティブ GUI の受入は対象 HEAD と実操作結果を別途記録する。
