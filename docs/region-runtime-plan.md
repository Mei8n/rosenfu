# 地域単位の読込・計算とマルチプレイ境界

2026-11-16。現行0.1の改善と将来設計を区別する。都市分割自体を目的にせず、計測でCPU・メモリ・通信の減少を確認する。TrainsWorldのコードは転載せず、設計の比較から独立実装する。

## 比較で確認したこと

固定参照: TrainsWorld `6b8ef91729e1e5812f3dcbaedd6c0a49fed6a84b`。

- [zones.md](https://github.com/circularsquare/trainsworld/blob/6b8ef91729e1e5812f3dcbaedd6c0a49fed6a84b/trainworld/docs/zones.md): 都市圏と非都市圏を需要地域として分割。線路の所有権やセーブを都市単位で別世界に分ける意味ではない。
- [demand-runtime.md](https://github.com/circularsquare/trainsworld/blob/6b8ef91729e1e5812f3dcbaedd6c0a49fed6a84b/trainworld/docs/demand-runtime.md): 駅の到達範囲に応じて都市需要packを保持し、都市間market packは別条件で保持する。閲覧のみの地域は軽量側で計算し、不要packを猶予後に解放する。WASM領域は縮小せず再利用。計算開始時には必要packが揃っていることを確認する。到達距離や猶予時間は同作のモデル固有で、そのままRosenfuへ採用しない。
- [architecture.md](https://github.com/circularsquare/trainsworld/blob/6b8ef91729e1e5812f3dcbaedd6c0a49fed6a84b/trainworld/docs/architecture.md): 旅客は個人の毎フレーム移動ではなく集団流動、列車描画と需要計算を分離する。これをマルチプレイ実装済みの証拠とは扱わない。

## 現行Rosenfuで採用する範囲

| 対象 | 現状と今回の変更 | 分割で切ってはいけないもの |
| --- | --- | --- |
| 水域 | 45地域の固定版を必要範囲で取得。今回、既設線の点対ごとの地域検索を一括集合照会に変更。投影境界は一回だけ計算し、同地域の重複結果生成を省く | 水域重複時のwet優先、境界接触、未取得と乾燥の区別、接続先の必要地域 |
| 道路・実在線 | 既存の地理タイルを利用。都市名へ再分割しない | タイル境界の接続、データ版、既設線が参照する取得根拠 |
| ワールド | 線路・駅・路線・系統は同じ権威あるグラフ | 都市を跨ぐ路線・系統、所有会社、Undo、保存参照 |
| 需要・流動 | 0.2以降。今回未実装 | 地域間OD、遠方新線による経路変更、会社間競争 |

一括地域照会は独立した区間の集合を使い、東京と札幌を結ぶ巨大な外接矩形へ変えない。関係ない中間地域の取得は増やさない。永続キャッシュやワールドrevisionの追加なしで同じ結果を返すため、Undo・読込・別ワールドへの切替後にも古い地域集合を再利用しない。既設線の判定方針・費用・保存形式は変更しない。

## マルチプレイに向けた現状監査と境界

現行はローカルの `WorldEditor` をMutexで直列化し、Rust側で候補を検証して確定する構造。道路の確定時にはworld tokenや原データ根拠、各編集にはexpected値などがあるが、すべての操作をマルチ対応と判断できる統一プロトコルはまだない。

今は、取得キャッシュと権威あるワールドの分離を維持し、読込順や画面位置が永続状態を直接書き換えないようにする。一括地域照会も読み取り専用で順序非依存。ネットワーク対戦を先に実装したり、架空の同期安全性を主張したりしない。

道路参照スナップショット付き着工は、参照の取り込みから建設・水域検証・保存上限確認までを一つのローカル候補に適用する。候補内で再び着工を確定せず、運行と固定ODを現在のワールドに照合した後、成功時だけ一度履歴を進める。照合で運行等の保存内容が変わったときは、確定直前に保存上限を再確認する。読込時の全体検証や参照整合性のルールは変えない。

将来のホストではこの検証と確定を同じ権威側操作として再利用する。送受信側に運行キャッシュやUndo全体を渡さず、確定前revision・一意command ID・適用後revisionと結果差分を扱う。再送・差分欠落時のsnapshot再同期は上記の設計上の境界であり、現行のローカル履歴revisionはネットワーク同期用ではない。

0.4の接続前に必要な実装:

1. サーバーが認証済み参加者と会社権限から操作を受け付け、共通revisionと一意command IDで順序を確定。クライアントからのWorldDraft全置換を対戦APIに流用しない。
2. 再送・途中参加で同一操作を二重適用しない。権威あるsnapshotと後続差分を原子的に切り替える。Undoは他人の変更を消す全体巻戻しにしない。
3. キャッシュはデータ版・地域IDをキーにした破棄可能な参照。必要な入力の版はホストで揃え、クライアントの通信失敗や画面外への移動をゲーム結果の違いにしない。未知データで続行する既存ルールはホストが一度だけ確定する。
4. 市境界を跨ぐグラフは一つの論理グラフとして扱う。地域別workerを採用する場合も境界ノードと需要を一意に所有し、重複計上を防ぐ。

## 需要分割の導入順（未実装）

0.2で小地域固定ODと全体参照計算を先に作る。静的需要packの版・範囲を固定し、同じ入力を全pack常駐と必要packのみで計算して総需要・経路配分が一致する試験を用意する。閲覧だけの地域と鉄道網が到達する地域を分けるが、都市間marketや遠方の乗換を単純な距離だけで落とさない。

その後CPU・RAM・再取得通信量・パン時の計算回数を計測して、需要packの保持/解放・軽量表示・依存関係による再計算を段階導入する。ワールド全体を常に複製するコスト、道路証拠の保持量、全国規模での水域集合照会は別々に計測する。0.1のGUI操作・描画改善と重複して同じファイルを変更しない。

## 無人進行と可視範囲からの独立（将来要件・未実装）

需要の基本単位はメッシュとし、長距離はゾーンを併用する。[需要・流動計画](demand-flow-plan.md)の人口/目的地からの潜在ODを、駅の有無や閲覧状態によって消さない。メッシュとゾーンの重複計上を防ぐ。

将来の権威側シミュレーションは、接続プレイヤーが0人でもheadlessで進行できる構造にする。世界時刻・操作順・モデル版・データ版・seed・計算epochを入力とし、クライアントの可視範囲、描画workerの有無、接続人数を需要・運行の計算対象を決める条件にしない。明示的な一時停止と、全員の切断は別の状態として扱う。

必要な計算packは、権威側の潜在OD・運行・地域間経路の依存関係から選ぶ。画面外でも需要や遠方への影響がある地域を落とさない。鉄道未到達の需要を集約して保持するなどの省力化は、全体参照計算との一致を確認して採用する。都市間の依存を可視地域だけで打ち切らない。

閲覧用packの解放は破棄可能な表示キャッシュにだけ作用させる。権威側の計算に必要な入力が未取得の場合と、クライアントの表示が未取得の場合を区別する。入力不足の扱いはホストがモデルごとに決め、クライアントの読込順で結果を変えない。既存の建設用水域の未知データ続行ルールを、将来の需要欠測へ無条件に流用しない。

受入試験は、同じ初期状態・操作列・世界時刻区間・seedで、表示なし/表示あり、0人/1人/複数人、異なる可視範囲を比較する。潜在OD・運行・輸送・収入の集計と権威状態が一致し、切断/再参加で時計や計算epochが二重進行しないことを確認する。必要pack常駐と遅延読込の結果も比較する。

ここで記載したheadless進行、需要・運行、ネットワーク同期は現行0.1で実装済みではない。需要は0.2以降、マルチ本体は0.4の計画であり、今回の地域集合照会の最適化と区別する。

## 検証

- 全国の登録境界、端点のみの接触、離れた複数地域、重複・順序入替、不正な末尾座標で旧独立照会と結果を比較する。
- セーブ読込後の遠方既設線、新規ワールド、既知水域の保持をsession回帰で確認する。
- `cargo test -p rosenfu-core --lib measure_batched_region_queries -- --ignored --nocapture` は10万線分の旧方式と一括方式の合成計測。壁時計の固定閾値をCI合否にしない。実機入力遅延やマルチプレイ性能の保証ではない。

2026-11-16 cloud Linuxでの合成計測（release、10万点対、1都市内の細分化線路）: 旧方式45.5〜49.5ms、一括方式4.3〜4.9ms。境界投影と重複した文字列/集合挿入を省く効果であり、通信速度・実機GUI・全国の実プレイで同じ比率を保証しない。地域ごとの都市需要分割そのものを実装した数値ではない。

### α0.2 道路参照付き着工の計測

同じ Linux release テストバイナリで、旧来の入れ子確定と新しい一候補を同じ合成ワールドに各6回適用し、対ごとに実行順を交替した。無人の合成ワールドに道路参照1枚・線路1本を追加する。着工時のネイティブ処理、直後の保存エンコード、返却スナップショットの非整形JSON量を分けて記録し、対の返却・保存バイトが完全一致することも検査する。

| 既設線形数 | 着工の中央値（旧 → 新） | 保存エンコードの中央値（旧 → 新） | IPC想定JSON / 保存本体 |
|---:|---:|---:|---:|
| 100 | 0.570 → 0.332 ms | 0.186 → 0.187 ms | 16,983 / 35,307 B |
| 1,000 | 5.626 → 3.487 ms | 2.312 → 1.948 ms | 160,790 / 334,814 B |
| 12,500 | 56.989 → 33.983 ms | 17.230 → 17.148 ms | 2,012,293 / 4,175,817 B |

各方式のバイナリを5回ずつ新規プロセスで交互に起動したときのピークRSS中央値は28,864 → 27,980 KiB。これらは同一ホストでの合成値であり、地図UIの往復時間や全国プレイ、保存の高速化を保証しない。この変更は着工時の再検証を減らすもので、保存方式・返却データ量や常時のプレビューを変更しない。過去からあるプレビュー側の計測は別経路。

再現: `cargo test --locked --release -p rosenfu-storage --test water_session measure_one_construction_candidate -- --ignored --nocapture`。方式ごとのRSSを調べる場合は、同じテストバイナリを `ROSENFU_CONSTRUCTION_BENCH_ARM=nested` または `single` で個別に起動する。通常の回帰では稼働中の列車、駅・系統参照、固定OD、Undo境界、失敗時の原子性を旧方式と比較する。

### α0.2 道路参照付きサマリープレビューの計測

サマリーは着工前後の踏切差分と道路データの確認結果を返す。道路の物理形状・高さ区分・検証済み範囲・継ぎ目情報の導出は、一回の全線形評価の中だけで共有する。ワールドやフレームをまたいだキャッシュにはしない。従来の範囲・交差・高さ・重複判定、候補ワールドの検証と返却形式は変更しない。古い候補は新しい道路参照を勝手に使わない。

合成済みの道路1,000本（各8点）、既設線形100 / 1,000 / 10,000本を用い、同じハーネスの Linux release 前後バイナリを3対交互に実行。各プロセスの1回目を除いた6試行の中央値を比較した。ワーカー内処理と、入力解析・スナップショット取得・出力エンコードは別計測。

| 既設線形数 | 1回の道路評価（旧 → 新） | サマリーワーカー（旧 → 新） |
|---:|---:|---:|
| 100 | 2.660 → 0.438 ms | 10.291 → 5.782 ms |
| 1,000 | 22.458 → 1.717 ms | 54.728 → 11.436 ms |
| 10,000 | 333.843 → 16.212 ms | 503.004 → 66.222 ms |

最大ケースでは単一計画の入力JSON140 B（実際のIPCエンベロープを含まない）・応答本体69 B・通常の保存本体4,387,604 Bは前後同じ。ロックとスナップショット取得は1.212 → 0.928 ms、応答エンコード2.830 → 1.280 µs。プロセス全体のピークRSS中央値は31,652 → 33,740 KiB。これは合成入力のネイティブ処理で、TauriのIPC往復、WebViewの描画遅延、全国実プレイを計測した値ではない。

再現: `cargo test --release --locked -p rosenfu-storage --test construction_preview_benchmark construction_summary_timings -- --ignored --nocapture`。

### α0.2 着工・保存上書き・再読込の計測（#198）

上の同じ合成ワールド・道路データで、短い線形を実際に着工し、既存の手動セーブを新しい視点とともに上書きし、新規エディタで同じスロットを開く。毎回同じ既設線形数から始め、編集済みワールドが視点を含めて一致することを検証する。着工、返却ワールドのJSON化、保存上書き、再読込を分け、合計時間と返却・保存バイト数も記録する。

```bash
for n in 100 1000 10000; do
  ROSENFU_EDIT_BENCH_ALIGNMENTS=$n cargo test --release --locked \
    -p rosenfu-storage --features standard-periodic-rail \
    --test construction_preview_benchmark construction_edit_save_reopen_timings \
    -- --ignored --exact --nocapture
done
```

各ケースは新規テストプロセスの1回目と、その後の6回を別に比較する。LinuxのピークRSSはワールド生成と照合を含むプロセス全体の値で、個別工程の増分ではない。再読込はエディタだけを作り直し、OSのファイルキャッシュは消去しない。この結果はWebViewの描画、IPC通信、未取得の地図読み込み、全国プレイの性能を含まない。


### α0.2 ワールド内の参考道路を表示（#197）

「地図・表示設定」の「ワールド内の参考道路を表示」を有効にすると、
表示範囲にかかる z14 の区画だけを既存の地理根拠ストアから展開する。
保存したワールドをオフラインで開き直した後でも、そのワールドが保持する
道路を確認できる。通常のオンライン道路表示や路線編集とは独立した参考表示。
未保持の区画を補完・再取得せず、データのない区画を「道路なし」と判定しない。

最大16区画（既存の生データ合計上限も維持）・4,000表示線分まで。大きな表示範囲は
拡大を案内し、線分を打ち切った場合は一部表示であることを伝える。元タイルの
バッファは区画境界で切り、表示枠外に描かない。展開は既存のLRUを使い、
キャッシュ退避がワールド内の地理根拠を削除することはない。画面や開いた
ワールドを切り替えた場合は、古い表示要求の結果を適用しない。
IPCに入るのは参考線分だけであり、元のタイルデータや着工可否は渡さない。

ワールド自体は従来どおり一つの権威あるグラフとして完全に検証して開く。
これは編集・運行の地域分割、基図のオフライン配信、または全国同時表示の保証ではない。
別ドキュメントの合成試験値をこの表示の性能測定として扱わない。

再現: `cargo test --locked -p rosenfu-core --lib ofm_evidence::viewport` と
`cargo test --locked -p rosenfu-storage --test retained_road_view`。
前者は遠く離れた区画を一枚ずつ展開し、選ばれなかった区画がLRUに入らないことを検査する。
後者はワールドの保存 → 通常読込 → 両地域の表示と保存内容の一致を確認する。
`npm test -- src/RetainedRoadLayer.test.tsx` は範囲移動・ワールド切替・Undoでの表示破棄を確認する。

### α0.2 着工確定時の最終セーブ容量検査（#198）

着工候補の線形・駅・水域の検証は維持する。着工確定時の容量は、中間案ではなく運行と固定ODを
引き継いだ最終状態で検査する。時間帯ダイヤを復元できない案は引き続き確定せず、履歴や操作対象を
更新する前に拒否する。地図・時間帯ダイヤ・セーブの形式や、プレビューの容量検査は変えない。

次の合成ベンチマークは既設線形100 / 1,000 / 10,000本に、設定済みの時間帯ダイヤと固定ODを持つ
ワールドを使う。旧処理と新処理で、道路参照1枚と線形1本を確定する。各規模の順序を交替させ、
確定処理時間と返却・保存バイト数を出力し、対の出力バイトの一致を検査する。
初回を除いた各方式の中央値を比較する。保存への実際の書込やWebViewは含まない。

```sh
cargo test --locked --release -p rosenfu-storage --features standard-periodic-rail \
  --test water_session measure_reconciled_construction_capacity -- --ignored --nocapture
```

個別プロセスのRSS比較には同じテストバイナリを使い、
`ROSENFU_FINAL_CAPACITY_ALIGNMENTS=10000` と
`ROSENFU_FINAL_CAPACITY_ARM=former` または `final` を指定する。この変更の時間・RSSは未測定。
